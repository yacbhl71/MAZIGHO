# MAZIGHO — sauvegarde, restauration et alerting

**État : configuration livrée, non activée en production.** Les tâches planifiées sont verrouillées par `MAZIGHO_OPS_ENABLED=true`. Aucun bucket AWS, clé, accès TiDB de lecture seule, sonde de métriques, ou instance TiDB de restauration n’a été créé par cette livraison. Ne pas confondre le déploiement des fichiers avec une protection opérationnelle.

## Architecture et calendrier

| Fonction | Fichier | Exécution après activation | Propriété |
| --- | --- | --- | --- |
| Snapshot DB | `scripts/ops/backup_db.py` + `.github/workflows/ops-backup-monitor.yml` | Chaque jour 02:13 UTC | Dump SQL cohérent en lecture seule → gzip → chiffrement `age` en mémoire/flux → S3 privé, versionné, verrouillé ; manifeste SHA-256 ; rétention SQL 30 jours minimum. |
| Médias | `scripts/ops/backup_blob.mjs` | Après le snapshot SQL | Énumère le **Vercel Blob actuel**, archive les couples pathname/ETag manquants vers S3 sous chiffrement `age`. Aucun appel de suppression Blob. |
| Restauration | `scripts/ops/restore_drill.py` + `.github/workflows/ops-restore-drill.yml` | Dimanche 03:43 UTC, **après activation distincte** | Télécharge la dernière sauvegarde, vérifie le SHA-256 du chiffré, déchiffre en flux dans un nouveau schéma sur une **autre instance**, vérifie `stores`, `users` et le nombre de boutiques ; efface uniquement le schéma d’essai créé. |
| Domaines clients | `scripts/ops/check_domains.py` | À 17 et 47 minutes de chaque heure | Lit les domaines actifs hors `*.mazigho.ch` dans `stores`; vérifie DNS public et certificat HTTPS ; échec du workflow + notification facultative. |
| Alertes précises | `ops/alerts/mazigho.rules.yml` | **Non actives** avant le raccordement des métriques et d’un moteur Prometheus/Alertmanager | 5xx > 2 % sur 5 min, trois échecs Stripe successifs, CPU ou RAM > 85 % durant 10 min, âge du backup et santé DNS. |

Le stockage actif des boutiques est **Vercel Blob**, et non S3 : le versionnage S3 protège **l’archive séparée**, pas les objets Blob avant leur première copie. Les quotas de plans FREE/BASIC/PRO (500 Mio / 1 Gio / 2 Gio) restent calculés sur les médias **actifs** de Blob ; l’archive est un coût d’infrastructure MAZIGHO distinct, jamais une consommation de quota du commerçant. Le RPO maximal du miroir quotidien est approximativement 24 heures ; une protection instantanée des uploads récents nécessiterait un double-écriture transactionnelle ou un événement d’upload, non livré ici. Les versions actuelles du miroir sont conservées tant que l’archivage existe ; seul un ancien exemplaire remplacé expire après 30 jours. Sans politique de purge des objets devenus orphelins, l’archive grandira : définir une politique de suppression conforme aux obligations de conservation avant montée en charge.

## Activation de la protection SQL et média

1. Choisir et autoriser **un bucket S3 de secours dédié** et sa région : l’opération crée une ressource susceptible d’être facturée. Lire les coûts de stockage, d’opérations et de transfert. Ne pas placer le bucket dans le projet public Vercel.
2. Créer une paire de clés `age` hors CI : la clé **publique** devient `BACKUP_AGE_RECIPIENT` ; la clé **privée** doit être conservée hors ligne et, si le test hebdomadaire est choisi, dans le secret `BACKUP_AGE_IDENTITY`. Conserver en coffre une copie de la clé privée : la perdre rend toutes les sauvegardes illisibles. Ne jamais remplacer une clé sans période de transition et exercice de déchiffrement.
3. Réviser `ops/backup/provision-s3.sh`, puis l’exécuter **par l’opérateur uniquement**, avec `--apply`, `BACKUP_S3_BUCKET` et `BACKUP_AWS_REGION`. Il crée un bucket privé avec Versioning, AES256, Object Lock GOVERNANCE 30 jours et `ops/backup/s3-lifecycle.json`. N’accorder **aucun** `s3:DeleteObject`, `s3:DeleteObjectVersion` ou `s3:BypassGovernanceRetention` au compte CI. Restreindre les droits CI à la liste, lecture, écriture des préfixes `database/daily/` et `media/objects/` et aux lectures de configuration du bucket. Object Lock Governance est contournable par une identité privilégiée : protéger le compte administrateur séparément.
4. Configurer dans les **GitHub Actions Secrets** du dépôt `BACKUP_DATABASE_URL` (utilisateur TiDB dédié avec `SELECT` et `SHOW VIEW`, sans écritures), `BACKUP_AGE_RECIPIENT`, `BACKUP_AWS_ACCESS_KEY_ID`, `BACKUP_AWS_SECRET_ACCESS_KEY`, `BACKUP_BLOB_READ_WRITE_TOKEN` (secret externe à Vercel : OIDC de Vercel n’est pas exploitable tel quel en CI). Éventuellement `OPS_ALERT_WEBHOOK_URL` pour un endpoint HTTPS d’alerte privé. Dans les **Variables** : `BACKUP_S3_BUCKET`, `BACKUP_AWS_REGION`. Utiliser une URL de connexion TiDB dont le certificat et le nom d’hôte sont vérifiables ; le client refuse autrement.
5. Une fois le bucket et les secrets revus, définir `MAZIGHO_OPS_ENABLED=true` dans GitHub Actions Variables, **puis** lancer un premier `workflow_dispatch` pour `backup`. Vérifier **deux objets SQL** (archive + manifeste) et le miroir média dans S3. Télécharger un objet `.age`, vérifier le SHA-256 du manifeste puis déchiffrer sur une machine contrôlée, sans afficher le contenu en logs. Activer les notifications de workflows GitHub et tester `OPS_ALERT_WEBHOOK_URL` si utilisé. En cas d’échec SQL ou média, le job échoue, il ne se contente pas d’un succès partiel. La prochaine tâche cron exécutera la sauvegarde à l’heure UTC indiquée ; désactiver la variable si le premier essai révèle une erreur.

**Attention TiDB :** TiDB Cloud **Starter gratuit** ne garde ses snapshots natifs qu’**un jour** et n’offre **pas** le PITR. Un Starter avec spending limit positif ou Essential peut garder 30 jours ; seul Essential propose le PITR (preview), Dedicated aussi selon la version. Le dump SQL chiffré quotidien assure 30 jours d’archives **même avec Starter**, mais **n’est pas du PITR**. Il n’est pas non plus une sauvegarde physique TiDB : vérifier à intervalle régulier sa compatibilité avec vues, triggers, événements, permissions et migrations ; planifier une fenêtre sans DDL pendant le dump.

## Répétition automatique de restauration et PITR fournisseur

Créer une **instance TiDB de test différente de la production**, joignable par GitHub Actions et permettant `CREATE DATABASE` / `DROP DATABASE` à un compte de restauration limité. Renseigner `RESTORE_DRILL_DATABASE_URL` (nom de base utilisé comme préfixe), `BACKUP_AGE_IDENTITY` (clé privée protégée) puis `MAZIGHO_RESTORE_DRILL_ENABLED=true`. Le workflow du dimanche crée un schéma unique, importe le dump et le détruit ; il échoue sur checksum invalide, données absentes ou déchiffrement impossible. La base **production ne reçoit aucune écriture** du test. Avant d’activer le secret de restauration en CI, faire un premier exercice contrôlé et autoriser le coût de l’instance. Ne jamais utiliser comme cible un alias de l’instance source ; le garde logiciel vérifie le nom d’hôte mais ne peut pas prouver qu’il s’agit d’un autre cluster.

Pour un **véritable test PITR**, utiliser TiDB Essential ou Dedicated, activer sa rétention 30 jours et son PITR natif, puis programmer une restauration dans une **nouvelle instance éphémère** à T−1h ; vérifier `stores` et `users`, l’heure retrouvable, RPO/RTO, puis supprimer cette seule instance d’exercice après validation. Sur Starter gratuit, cette étape est techniquement **impossible** ; le workflow hebdomadaire ci-dessus teste un **snapshot**, pas la récupération à un instant. L’API publique TiDB v1beta de restauration ne prend pas en charge Starter. Ne pas automatiser la création/suppression d’instances facturables sans le niveau de service choisi et un compte dédié approuvé.

## Alertes, contrat d’ingestion et notifications

Importer `ops/alerts/mazigho.rules.yml` dans un Prometheus avec Alertmanager et brancher les sources suivantes. Les noms de métriques sont un **contrat**, pas des métriques déjà émis par MAZIGHO. Ne jamais annoncer les alertes comme actives avant d’avoir testé le trajet jusqu’à la notification.

| Signal | Producteur nécessaire | Sens et vérification |
| --- | --- | --- |
| `mazigho_http_requests_total{host,status}` | Log Drain Vercel vers collecteur durable **non échantillonné**, qui compte toutes les requêtes edge sur `www.mazigho.ch` / `mazigho.ch` / `studio.mazigho.ch` | Ratio de `increase()` 5xx / toutes réponses par host sur 5 min, > 0,02 ; alerte distincte d’indisponibilité et de télémétrie silencieuse recommandée. Une sonde ne mesure **pas** ce taux réel. |
| `mazigho_stripe_webhook_consecutive_failures{provider="stripe",mode}` | Agrégateur persistant des **livraisons Stripe** (événements 5xx / timeout / succès vérifié), réconcilié avec la liste des webhooks Stripe | Passe à 3 après trois tentatives échouées consécutives ; remet à 0 après une livraison vérifiée réussie. Ne pas utiliser une variable en mémoire d’une fonction Vercel ; ne pas compter les rejets de signatures comme un succès. |
| `mazigho_infra_cpu_usage_ratio{service}` et `mazigho_infra_memory_usage_ratio{service}` | Exporteur du nœud TiDB ou VM **si le plan fournit ces mesures** ; ratios entre 0 et 1 | > 0,85 pendant 10 min. Les fonctions Vercel n’ont pas de CPU/RAM hôte persistant que l’on pourrait mesurer ainsi. |
| `mazigho_backup_last_success_timestamp_seconds` et `mazigho_custom_domain_valid{host}` | Collecteur de résultat du workflow SQL et sonde DNS | Sauvegarde > 26 h, DNS/TLS faux 10 min ; les workflows GitHub signalent déjà une erreur dès leur exécution, même avant le collecteur. |

Les alertes natives [Vercel](https://vercel.com/docs/alerts/configure-alerts) reposent sur une **anomalie statistique** 5xx et sont disponibles sur Pro + Observability Plus / Enterprise ; elles ne matérialisent **pas** exactement le seuil > 2 %. Les alertes TiDB [natives](https://docs.pingcap.com/tidbcloud/monitor-built-in-alerting/) sont réservées aux plans Essential/Premium/Dedicated, avec des seuils CPU/mémoire parfois éditables. Une installation Prometheus et un Log Drain nécessitent un hébergement et des accès supplémentaires : aucun collecteur ni alert routing n’a été activé ici. Tester chaque règle avec données synthétiques avant mise en service. Les workflows DNS interrogent la table `stores` ; les sous-domaines MAZIGHO sont exclus du lot « domaines personnalisés ». Une anomalie DNS ne change jamais le routage client automatiquement.

## Confidentialité, exploitation et limites

Le Workspace IA est chiffré **dans la base applicative**. Le dump copie ses ciphertexts, sans appel à une fonction de déchiffrement Workspace. Le dump entier et chaque média archivé sont en plus chiffrés `age` **avant tout envoi S3**. Le manifeste SQL ne contient ni mot de passe ni contenu boutique. La restauration d’essai lit les ciphertexts sans les déchiffrer applicativement ; le secret applicatif de chiffrement du Workspace doit être sauvegardé séparément en coffre, avec rotation documentée : **sans lui, les données Workspace restaurées restent illisibles**. Pour les médias publics, l’archive est néanmoins privée et chiffrée ; les copies ne sont jamais intégrées dans le quota commercial.

Ne pas rendre le compte CI administrateur TiDB ni AWS, ne pas exposer les secrets dans les logs, déployer les collecteurs hors fonction Vercel éphémère, et vérifier le délai de sauvegarde effectif et l’augmentation des coûts du miroir (liste Blob, transfert, versions S3). Un exercice hebdomadaire de snapshot et un exercice PITR natif périodique sont **deux** contrôles différents. Une restauration d’archive sur un clone ne restaure pas les secrets, les DNS, les identités TiDB ni les ressources Vercel ; conserver leurs configurations dans un coffre et un runbook séparé.
